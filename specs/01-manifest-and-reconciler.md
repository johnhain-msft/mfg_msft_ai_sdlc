## 1. Objective and non-goals

### Objective
Define the target state in which an operator points the orchestrator at any GitHub repositories — upstream sources and downstream hubs — by editing one declarative manifest, `sdlc.yaml`, and the engine deterministically turns that manifest into the complete, strictly compiled automation set, with no per-repository setup and no server outside GitHub Actions. This spec produces `schemas/sdlc.schema.json` (the manifest JSON Schema, including the `projectKey`, `upstreamKey` and `upstreamSlug` patterns and the `deconflictInRepoSchedules` enum) [F39], `sdlc.yaml` (the portfolio reference preset: `johnhain-msft/gh-admin-msft`, `ms-mfg-community/day-in-the-life-copilot-lab`, `ms-mfg-community/github-pipeline-showcase` and `githubschool/gh-github-intermediate-template` cascading into `johnhain-msft/portfolio` — data, not engine logic), `src/reconcile.mjs` (the repository-agnostic reconciler), `.github/workflows/aw.json` (`strict: true` and, where the compiler accepts the key, `protected_files.exclude`; AC55) [F15, F23], and the generated `.github/workflows/drift-<projectKey>.md`, `.github/workflows/cascade-router.yml`, `.github/workflows/cascade-mechanical-<edgeId>.md`, `.github/workflows/cascade-ai-<edgeId>.md`, `.github/workflows/sdlc-onboard.md` and `.github/workflows/shared/*.md`, each `gh-aw` source with its compiled `.lock.yml`. The `gh-aw` tool lets developers define repository automation as Markdown with YAML frontmatter, and the `gh aw` CLI extension compiles each workflow into a standard GitHub Actions workflow [F9]; the `.md` sources and the generated `.lock.yml` files are committed together [F12], and a central automation repository can hold the workflows, schedules and credentials while the target repositories need no installed workflows [F38]. The reconciler therefore validates the manifest against the `securityBaseline` that `S5` sends in contract `C1`, renders the `gh-aw` frontmatter policies (`on.bots`, `concurrency`, `permissions`, `safe-outputs.threat-detection`, `protected-files`, `allowed-files`, `exclude-lock-yml`, deterministic branch identity, `reviewers`, `auto-merge: false`), compiles them with `gh aw compile --strict --purge --json` [F16, F22], rolls back on any failure, and is idempotent, so that one run after any manifest change — by hand or through `sdlc onboard` — brings every generated file back in line with the manifest. It is the receiver of contract `C1` (`S5` to `S1`) and the producer of contracts `C2` (to `S2`), `C3` (to `S3`) and `C4` (to `S4`) [F39, F40, F41, F42]. It matters to an operator because adding a repository, a dependency edge or a watched URL becomes a data edit that reconciles into reviewed, reproducible, least-privilege workflows instead of hand-written per-repository automation.

### Non-goals
- No external always-on webhook servers, external databases or non-GitHub compute: every generated workflow runs as GitHub Actions compiled by `gh-aw` [F9], and this spec adds no server, queue or datastore.
- No automated pull-request merging: `auto-merge` is forbidden on every `safe-outputs.create-pull-request` handler and every CLI flow, the option itself accepts true, false or a merge method [F33], and this spec only ever renders `auto-merge: false`; every automated pull request requires explicit human review and merge.
- No automated regeneration of `/pipeline-showcase/media/pipeline-demo.svg`.
- No automatic bump of `gh_aw_schema_version`, and no automated editing or recompiling of the `.github/workflows/*.lock.yml` files of `ms-mfg-community/day-in-the-life-copilot-lab`: the reconciler writes workflows only in the orchestrator repository.
- No Azure Container Apps runtime or `Microsoft.App/sandboxGroups` infrastructure and no live Azure entitlement tests.
- No shipping of customer-specific authoring tools from `githubschool/gh-github-intermediate-template` [F8], and no rewriting of upstream lab prose during scheduled staleness sweeps.
- Stream boundary — not in this spec: runtime drift and modernization evaluation, snapshots under `/tmp/gh-aw/agent/` and open-PR deduplication (`S2`, SPEC-02); the routing logic of `cascade-router.yml`, conditional-GET polling, `src/update-poll-state.mjs` and every write of `SDLC_SYNC_STATE_<SLUG>` (`S3`, SPEC-03); `src/lab-studio-drift.mjs`, `src/bump-studio-revision-pins.mjs`, `src/verify-immutable-gates.mjs` and the adaptation and verification logic (`S4`, SPEC-04); `aw.yml`, `bin/sdlc-bootstrap.mjs`, `bin/sdlc-onboard.mjs`, GitHub App registration and installation, Actions variables and secrets, and disabling in-repository schedules (`S5`, SPEC-05).
- This spec does not commit, push, open pull requests or issues, or call any GitHub write API, and it resolves no open question: every claim graded CONTRADICTED is carried in §4 and gated there, not assumed.

**Compile-time verification notes (gh-aw v1.0.1, recorded by the implementing issue on 2026-11-05).** These are observations of the pinned compiler run against the rendered preset, made at compile time; a verifier has not graded them and no live Actions run was performed.

1. *Strict-mode custom jobs (the note above).* `gh aw compile --strict --purge --json` of v1.0.1 accepts the custom jobs of AC35 and AC36: the eight preset workflows compile with `valid: true` and no error, so failure reporting does not fall back to `safe-outputs` issue reporting and AC35 and AC36 need no amendment on that point.
2. *The `safe_outputs` condition (F21, AC29).* The compiler's own condition for the `safe_outputs` job is `(!cancelled()) && needs.agent.result != 'skipped' && needs.detection.result == 'success'` and for the `detection` job `always() && needs.agent.result != 'skipped'`. The `detection` job publishes the outputs `detection_conclusion`, `detection_reason`, `detection_success` and `run_detection`; `needs.detection.outputs.success`, the form that F21 quotes from the documentation, is not one of them. AC29 therefore observes the result form, which holds the same gate: `safe_outputs` is skipped unless `detection` succeeded.
3. *The `agent` job is not part of those conditions (AC29, AC53).* gh-aw places `post-steps:` at the end of the `agent` job, after the step that ingests the agent output and before the artifact uploads that run on `always()`, so a failing verification step fails the `agent` job after the patch and the safe outputs were recorded. Neither condition of note 2 requires `needs.agent.result == 'success'`, so after a failing gate `detection` and `safe_outputs` still run and the pull request is opened, contrary to the behaviour that SPEC-02 AC29 and SPEC-04 AC72 rely on. The run-time effect is derived from those conditions under the GitHub Actions `needs` semantics (`tests/s1/lock-gates.test.mjs`) and is not observed in a live run.
4. *`protected_files` in `aw.json` (F23, AC55).* The repository config schema of v1.0.1 (`repo_config_schema.json`, `additionalProperties: false`) has no `protected_files` property: `gh aw compile --strict --json` marks every workflow invalid with `failed to load aw.json ... additional properties 'protected_files' not allowed` for any `aw.json` that carries the key, `protected_files.exclude: []` included.
