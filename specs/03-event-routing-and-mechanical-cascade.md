## 1. Objective and non-goals

### Objective
This spec defines the runtime behaviour of the orchestrator's cross-repository event router, its single durable state, and its deterministic mechanical downstream cascade. The artifacts are `.github/workflows/cascade-router.yml` (rendered from `sdlc.yaml` `dependencyEdges[]` by SPEC-01, behaviour owned here), the router's decision procedure in `src/route-upstream.mjs`, the sole state writer `src/update-poll-state.mjs`, the shapes in `schemas/sdlc-routing.schema.json`, and the mechanical workflow `.github/workflows/cascade-mechanical-ghec-admin.md` with its compiled `.lock.yml` (rendered by SPEC-01, runtime behaviour owned here). The router detects any advance of an upstream default branch — from an optional `repository_dispatch` signal [F51–F54, F63], from a schedule, or from a manual `workflow_dispatch` carrying the boolean `reset_blocked` [F64] — using ETag conditional requests, so that an unchanged upstream answers `304 Not Modified` without consuming primary rate-limit points when the request carries a correct `Authorization` header [F59, F60]. It compares the observed head with a 14-field poll-state object kept in one Actions variable `SDLC_SYNC_STATE_<SLUG>` per edge [F66, F67], short-circuits commit-only and timestamp-only advances through edge-declared preflight checks [F14, F26, F29, F30] and records them as `lastNoopHeadSha`, and otherwise dispatches the cascade workflow asynchronously with `return_run_details: true` [F47, F55, F58]. For `mode: "mechanical"` edges the dispatched workflow imports the upstream into the downstream under `allowed-files: ["public/ghec-admin/**"]` [F44], gates the result in `post-steps:` [F36], opens one pull request through `safe-outputs.create-pull-request` [F39, F41], and lets `src/update-poll-state.mjs` verify that pull request before any state advances, failing closed after two attempts on the same SHA. The spec honours contracts C3 (the receiving side of `S1 -> S3`), C6, C7 (the `S3` side, shared with SPEC-04) and C8 of `plan.md` §5 [F70–F73]. It matters to an operator who points the orchestrator at a repository because every upstream advance is routed once, a no-op advance opens no downstream pull request, a SHA that fails twice stops until a human changes the downstream or sets one boolean, and the engine contains no repository names: the four-upstream fleet is `sdlc.yaml` data.

### Non-goals
- No always-on webhook servers, external databases or non-GitHub compute: the router and the cascade run only as GitHub Actions workflows, and state lives only in Actions variables [F66, F67].
- No automated pull-request merging: `auto-merge` is `false` on every `safe-outputs.create-pull-request` this spec configures [F45], S3 never calls a merge endpoint, and every cascade pull request requires explicit human review.
- No automated regeneration of `pipeline-demo.svg`: the pipeline-showcase preflight only decides whether captured run data changed [F14, F26].
- No automatic bump of `gh_aw_schema_version` and no editing or recompiling of the lab repository's `.github/workflows/*.lock.yml`.
- No Azure Container Apps or sandbox infrastructure and no live Azure entitlement tests.
- No shipping of customer-specific authoring tools and no rewriting of upstream lab prose.
- Stream boundary: SPEC-01 owns `sdlc.yaml`, `schemas/sdlc.schema.json`, `src/reconcile.mjs` and the rendering and graph validation of `cascade-router.yml` and the cascade workflows (`OQ38`–`OQ43`); SPEC-02 owns the drift workflows (`OQ37`); SPEC-04 owns the AI-adaptation workflows, the three helper CLIs and the dispatched run lifecycle (`OQ11`, `OQ15`, `OQ21`); SPEC-05 owns bootstrap, the GitHub App registration and the create-if-missing seeding of `SDLC_SYNC_STATE_<SLUG>`.
- No open question is resolved by this spec: `OQ1`, `OQ2`, `OQ3`, `OQ45`, `OQ46`, `OQ47`, `OQ48` and `OQ51` are carried in §4 and gate the criteria that name them.

## 8. Implementation amendments (S3 development stage)

Each entry changes how an acceptance criterion is satisfied or tested; none lowers what it requires. Sources are primary documents opened on 2026-11-07 (rate limits, best practices, `GITHUB_TOKEN` and App-permission pages of docs.github.com), the pinned source of `actions/create-github-app-token` at `fee1f7d63c2ff003460e3d139729b119787bc349` (`lib/get-permissions-from-inputs.js`, `lib/main.js`), the 2022-11-28 OpenAPI description of `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches` (`return_run_details: true` answers `200` with `workflow_run_id`, `run_url`, `html_url`), and code of this repository.

**Token and authentication (AC12, AC29, AC30, AC32, AC46, AC49, AC59, AC63; SPEC-01 AC16, AC35; SPEC-04 AC17, AC51, AC52).**
1. The step `actions/create-github-app-token@v2` of `finalize_poll_state` and `escalate_failure` names `permission-contents: read`, `permission-pull-requests: read` and `permission-variables: write`. The action stops inheriting the installation's permissions as soon as any `permission-*` input is given, so the earlier claim (AC32) that the token inherits the installation's permissions was wrong, and a token that named only the first two could not read or write `SDLC_SYNC_STATE_<SLUG>`. The step compiles under `gh aw compile --strict` (gh-aw v1.0.1); `securityBaseline.grantedAppPermissions` is unchanged. `checkRendered` rejects a cascade token step that lacks one of the three.
2. The router job receives `APP_CLIENT_ID` and `APP_PRIVATE_KEY` (SPEC-01 AC31), not `GH_TOKEN`. `src/route-upstream.mjs` signs an App JWT and exchanges it for a write token (the orchestrator owner's installation, the orchestrator repository only, `variables: write` and `actions: write`: the state, the dispatch, the run status) and a read token per owner (`contents`, `pull_requests` and `actions` read: every read of an upstream and a downstream repository, and the checkouts). A preflight command sees only a read token, as `GH_TOKEN`. The exchange `POST /app/installations/{id}/access_tokens` is therefore a non-`GET` request of the router (AC29); it changes nothing in any repository. An upstream whose owner has no installation is read with the read token of the orchestrator's owner, which works for a public repository only; the run says so.
3. Which events a `GITHUB_TOKEN` can use to start runs (OQ45, re-read): events that it creates start no run, except `workflow_dispatch` and `repository_dispatch`, which always do, and `pull_request` `opened`, `synchronize` and `reopened`, which start runs that wait for approval. S3 relies on none: it dispatches with an App token, and `ISSUES_TOKEN` (the job's `GITHUB_TOKEN`) only lists, creates and comments on issues.
4. Insufficient permissions (OQ51, re-read): a REST request answers `403` and an `X-Accepted-GitHub-Permissions` header; GraphQL answers `401`. S3 is REST-only (AC33), and a failure names the status, the path and that header. Git over HTTP uses `x-access-token` basic authentication with the Contents permission.

**Rate limits and errors (AC27, AC32, AC37, AC39; OQ46, re-read).**
5. The documentation lists three independent bounds: do not retry before `x-ratelimit-reset` when `x-ratelimit-remaining` is `0`; do not retry before `retry-after` seconds when it is present; otherwise wait at least a minute and back off exponentially (the best-practices page lists `retry-after` first, the rate-limit page lists the primary limit separately). AC27's order is kept (primary limit, then `retry-after`, then 60 seconds doubled), and when the primary limit and `retry-after` are both present the later of the two is waited, so that neither bound is retried early. Every decision logs the status and the three header values that it acted on; the total wait never passes the 30-minute timeout of the job less three minutes kept for the failure issue. The best-practices advice to pause a second between many mutative requests does not bind a run that makes at most three; a dispatch is followed by the five seconds of AC37.
6. The documentation advises following redirects; S3 does not, because the credential goes to the configured API origin only and `sdlc.yaml` is the single source of repository names. A `301`, `302`, `307` or `308` fails the job with its `location`, naming the repository that moved.
7. OQ47 (GraphQL limits) and OQ48 (access conditions of reusable workflows) do not bind this implementation: it uses neither (AC31, AC33 are `rg` checks).

**Preflights and checkouts (AC20-AC23, AC28, AC40).**
8. The router job checks out only the orchestrator. The script creates `$GITHUB_WORKSPACE/<downstream name>` and `$GITHUB_WORKSPACE/upstream/<upstream name>` itself (a fetch of the exact commit; an existing directory that is not a clean checkout at the wanted commit is never overwritten), and runs `npm ci --include=dev --ignore-scripts` in the downstream only when a preflight command is an `npm` or `npx` command.
9. AC20's combined `set +e` script is run as one bash per command, each with its own exit status and output: the report of `sync:workshop-source` and the JSON of the studio helper have to be read separately, and `rc1` alone never decides. The bindings, the working directory, the absence of `--accept` and the classification are as specified. The commands are told apart by their shape (a command that runs `sync:workshop-source`; one that runs `lab-studio-drift.mjs`; a `gh api` listing of `actions/runs`; any other command, whose exit status `0`, `1` or other means no difference, a difference or a failure).
10. AC22: the listing of the upstream's runs is a REST `GET` made by the router with the read token, compared with the ids of the `RUNS` array that it reads from the capture script of the downstream at the head that it read; the capture runs in an isolated temporary clone of the downstream under `RUNNER_TEMP`, and what it wrote is compared with the committed `run-data.json` with `snapshotAt` stripped. The router's own checkout of the downstream is never written, which is how "restore the worktree" is met. AC23: the upstream checkout holds both commits (the whole history when a command names `LAST_MERGED_SHA`); the fixture repository of its test is a recipe under `tests/s3/fixtures/git/` that the test turns into real repositories, because a nested repository cannot be committed.
11. The `sync_scope` of a dispatch is chosen within the `syncScopes` of the edge's entry in `sdlc.yaml`; a scope that the edge's workflow does not accept is replaced by one that it does.

**The mechanical workflow as compiled (AC3, AC4, AC46, AC56, AC61, AC62).**
12. AC4's handler also carries `exclude-lock-yml: true` and `protected-files: { policy: "blocked", exclude: [] }` (SPEC-01 AC34, AC64).
13. gh-aw inserts a `ghes-host-config` step ahead of the `app_token` step of a custom job and wraps the `if` of `finalize_poll_state` in a detection-success conjunct (`escalate_failure` opts out with `detection-gate: status-only`); the tests check that `app_token` is the first authored step and that the compiled `if` contains the stated condition. The compiler's own `conclusion` job holds `contents: write` and `pull-requests: write` beside `safe_outputs` (AC61): no job that this repository authors does. The compiled `if` of `detection` and `safe_outputs` contains `always()` or `!cancelled()` (AC62): it is a conjunct of `needs.agent.result == 'success'`, so a failed agent never reaches them.
14. Two holes found by running the rendered `post-steps:` for real, in separate bash processes against real git repositories (`tests/s3/mechanical-gate.test.mjs`), and closed in `src/reconcile.mjs`. (a) A failed import was a success. The importer's re-read source (OQ1-OQ3; `scripts/import-ghec-admin.mjs` lines 18-20, 73, 82, 161, 182, 218) throws on its five triggers before its first write to `public/ghec-admin` (the writes start at line 222; the guard of OQ3 comes after the temporary build and the upstream build of lines 37-42, which write only outside the destination), so a failed import leaves a clean tree and no commit; the clean-tree and allowed-paths checks accepted that, the builds passed, and `finalize_poll_state` recorded `noop-no-changes` for a target that was never imported. A new check, ahead of the builds, requires the edge's provenance file, at its JSON pointer, to name `upstream_sha` (the importer records the revision of the checkout it read, which is pinned to `upstream_sha`). (b) `git diff --name-only` names only the destination of a rename, so moving a file from outside the allowed paths into them hid the deletion of the source; the check now passes `--no-renames`.
15. AC64: no source or test of S3 names the importer's libraries or options; the only thing S3 knows about it is the edge's command with `<checkout>` bound to the absolute upstream path.

**Tests (AC67, AC69).**
16. The stub of AC67 is served in process through the injected `fetch`, and `GITHUB_API_URL` names a loopback origin on which nothing listens: hundreds of loopback connections crash a Node.js 24.0-24.15 process on Windows (`tests/s5/helpers/no-network.mjs`). `tests/s3/no-remote-writes.test.mjs` poisons everything that could reach the network and asserts that nothing is attempted.
17. AC69: every secret (the private key in each of its spellings, every token, the signed JWT, an Authorization header value) is registered as soon as the script holds it, and every line, the decision log and every issue body pass through one redactor, whatever the source: a server that echoes a header, a preflight command that prints its environment, an error that quotes a request.

**Correlation id of the cascade (AC46, AC49, AC52, AC63; SPEC-01 AC36; SPEC-04 AC51).**
18. A cascade is dispatched as a run of its own, so the correlation id that the router generated (AC52) reaches the `[sdlc-failure]` issue of `src/update-poll-state.mjs` only if the step passes it on. It did not: the script named `run-<run id>-<attempt>` of the cascade's own run, an id that the event never had, so an operator could not match the issue to the decision or the dispatch that caused it. `pollStateEnv` of `src/reconcile.mjs` now binds `CORRELATION_ID: ${{ inputs.correlation_id }}` in the script step of `finalize_poll_state` and `escalate_failure` of all four cascades (an `env` entry, never an expression inside the command text), and the script writes that id into the body and into the comments of the issue on each of its three paths to one (a verification failure, a failed request of the success path, `--record-failure`). The id that the run implies stays as the fallback for an empty input (a manual dispatch) and for one that is not shaped like `schemas/sdlc-routing.schema.json#/$defs/CorrelationId`, which a person could have typed and which must not reach the table of an issue; the failure is recorded either way, and the log says that the value was not used, not what it was. The renderer change is one `env` entry, made under S3's AC52; SPEC-01 AC36 and SPEC-04 AC51 name it. The workflows compile under `gh aw compile --strict` (gh-aw v1.0.1).

**Not exercised by any test (production gaps).** No live Actions run, no fetch of an exact commit or clone against the real GitHub, no `npm ci` of the real downstream and no Node.js version check on the router's runner; the Workflows permission is not requested, on the reading that a read of a repository that contains `.github/workflows` needs Contents only; the `schedule` trigger routes every edge on every scheduled run, so an edge's own `schedule` is informational; a cross-owner upstream needs an installation of the App to be read when private.
