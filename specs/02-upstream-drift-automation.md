## 1. Objective and non-goals

### Objective
Make every `sdlc.yaml` project whose `driftAudit.enabled` is `true` produce, through the SPEC-01 reconciler, a parameterized central `gh-aw` upkeep workflow (`.github/workflows/drift-<projectKey>.md` and its `.lock.yml`) that checks out the project's repository, runs deterministic `pre-agent-steps:` (hooks that run just before MCP startup and engine execution, whose files in `/tmp/gh-aw/agent/` are uploaded as artifacts and available to the agent [F38, F39]) to deduplicate against open pull requests and to snapshot the project's `knowledgeSources.watchUrls` and `knowledgeSources.packageManifests` into `/tmp/gh-aw/agent/sources/`, lets the agent evaluate documentation drift, library and framework upgrades or code-quality improvements according to the project's `upkeepStrategy` and registration `instructions` (corroborated through the `microsoft-learn` and `context7` MCP servers and `web-fetch`), runs the project's `buildCommands` and commits the rebuilt outputs before `create_pull_request`, runs the project's `verifyCommands` in `post-steps:` (which run after the engine finishes [F38]), and only then opens or updates a verified pull request on an `sdlc/`-prefixed branch through `safe-outputs.create-pull-request`; when any gate fails it runs no `safe_outputs` and opens a deduplicated `sdlc-gate-failure` issue in `johnhain-msft/mfg_msft_ai_sdlc` instead. This spec produces the runtime scripts under `src/drift/`, the prompt fragments under `prompts/drift/`, `src/snapshot-watch-sources.mjs`, `src/validate-copilot-lab-audit.mjs`, the schemas `schemas/drift-compile-ack.schema.json` and `schemas/github-pull-request-response.schema.json`, the preset `driftAudit` entries in `sdlc.yaml` with `instructions/gh-admin-msft.md`, `instructions/copilot-lab.md` and `instructions/self-improving-agents.md`, and the tests under `tests/s2/`; it honours contract C2 (`S1` renders the workflows, `S2` consumes them and owns runtime evaluation and the artifacts under `/tmp/gh-aw/agent/`) and contract C5 (`S2` to the upstream repositories) of `plan.md` §5 [F58, F59]. It matters to an operator who points the orchestrator at a repository because a `driftAudit` block alone, not a workflow installed in that repository, yields verified upkeep pull requests: the engine code is repository-agnostic, and the shipped fleet for `johnhain-msft/gh-admin-msft` and `ms-mfg-community/day-in-the-life-copilot-lab` is data in `sdlc.yaml` that coexists with the lab's own scheduled `weekly-content-audit.md` and `self-improving-agents.md` workflows [F2, F13] without opening duplicate pull requests, rewriting upstream prose, bumping `gh_aw_schema_version` or editing `.github/workflows/**`.

### Non-goals
- External always-on webhook servers, external databases and non-GitHub compute: every drift workflow runs on GitHub Actions only, and this spec adds none.
- Automated pull-request merging: `auto-merge` is forbidden on every `safe-outputs.create-pull-request` block and flow this spec owns; the option otherwise accepts `true` or a merge method [F53], and the lab's own self-improvement workflow states 'No autonomous merges, ever' [F17]. Every automated pull request needs explicit human review and merge.
- Automated regeneration of `/pipeline-showcase/media/pipeline-demo.svg` from live Playwright screenshots; the pipeline showcase belongs to SPEC-04.
- Automatic bumping of `gh_aw_schema_version` (`0.86.2` [F18]) and automated editing or recompiling of `.github/workflows/*.lock.yml` inside `ms-mfg-community/day-in-the-life-copilot-lab` during routine drift sweeps: `S2` reports new `github/gh-aw` releases in `docs/_meta/audit-report.md` [F7, F8, F10] and enforces `exclude-lock-yml: true` [F51] and `protected-files` with `policy: "blocked"` [F52] on `.github/workflows/**`.
- Azure Container Apps runtime infrastructure, `Microsoft.App/sandboxGroups` Bicep or Terraform, and live Azure entitlement tests (`npm run test:live -w server`).
- Customer-specific authoring tools from `githubschool/gh-github-intermediate-template`, and rewriting upstream lab prose during scheduled staleness sweeps: the lab's own audit allows only mechanical edits and says 'Do not rewrite prose' [F1, F9].
- Work that belongs to other specs: the manifest schema, `src/reconcile.mjs`, rendering, compile-time rejection, `on.bots`, `network.allowed` extraction, `concurrency` and the static `safe-outputs` policy belong to SPEC-01; poll state, the cascade router and the mechanical downstream cascade belong to SPEC-03; AI-authored downstream adaptation belongs to SPEC-04; packaging, bootstrap, onboarding, credentials and `deconflictInRepoSchedules` belong to SPEC-05.
- New schema fields: the `driftAudit` shape is that of contract C2 [F58]; `remediationPolicy` (named in the `S2` row of `plan.md` §2) and `<workflowKey>` (named in the branch pattern of contract C5) are not fields of that shape, and this spec adds neither.
- Resolving any open question: `OQ22`–`OQ25`, `OQ28`–`OQ29` and `OQ34`–`OQ37` stay in §4 and gate the criteria named there.

This note does not claim that the sandbox of the engine step makes its own `GITHUB_ENV` file unreachable: that was not observed in a live run. What the tests show is that the validator no longer reads a file that the agent is told to write. The round-2 review (`judge`) found that this closed one of several ways in which the agent decides what the rule compares: the compiled agent step allows `git` with any arguments (`shell(git:*)`), and the validator read the checkout that the agent had just worked in. In `gh-aw` v1.0.1 the safe-output tool `create_pull_request` writes `/tmp/gh-aw/aw-<branch>.patch` (the output of `git format-patch`) and, when it makes one, `/tmp/gh-aw/aw-<branch>.bundle` during the agent step, and the `safe_outputs` job applies that patch (`git am --3way`) whatever HEAD is by then (`generate_git_patch.cjs`, `generate_git_bundle.cjs` and `create_pull_request.cjs` of `github/gh-aw-actions` at the commit `221ba4f4319de6b8e809d1a15528b3ae6a818aa5` that the lock files pin, read locally). An agent that committed a `gh_aw_schema_version` bump or an edit under `.github/workflows/` on a branch, called the tool and ran `git switch` back to the base branch left a HEAD that equalled the base commit, which the rule accepted, and a patch that still carried the change. The validator now applies the rule of AC22 to HEAD, the index and the working tree, as before, and also to every commit that is reachable from a ref and not from the base commit (`git --no-replace-objects rev-list --all --not <base>`), to every message of every `aw-*.patch` file in the directory above `--out` (`/tmp/gh-aw/` in the compiled jobs; each message is applied in turn to the base commit in a scratch repository, which gives one tree per message) and to every commit of every `aw-*.bundle` file there. It applies the registry-key and report-section checks of AC23 to the working tree and to the tip of each of those revisions, so that a branch switch cannot hide or spoof them. A patch or a bundle that cannot be read or applied, and more than 2000 commits ahead of the base commit, fail the rule. **The validator's own file.** `prepare-run.mjs` stages a copy of `src/validate-*.mjs` and of `src/drift/lib/` read-only under `${RUNNER_TEMP}/gh-aw/sdlc-validator/` before the agent starts, and the compiled `awf` command mounts `${RUNNER_TEMP}/gh-aw` read-only (`--mount "${RUNNER_TEMP}/gh-aw:${RUNNER_TEMP}/gh-aw:ro"`). The first `verifyCommands` entry of each lab project compares the validator and `src/drift/lib/` of `$GITHUB_WORKSPACE` with that copy (`cmp -s` and `diff -rq`) and exits `1` before it runs `node "$GITHUB_WORKSPACE/src/validate-copilot-lab-audit.mjs"` when they differ or when no copy was staged; AC5 allows that one write. A comparison with `git diff HEAD` was not chosen, because the agent can commit the file that it rewrote, and a comparison of blob ids with the commit that the run started from was not built, because the staged copy needs nothing from the `.git` directory that the agent can write. *Closed in round 2 of the second run (2026-11-07), after the first review of that round found that the validator itself started programs that the agent had configured in the checkout.* **The checkout's own configuration.** The version of the patch and bundle check above ran `git diff <base>`, `git ls-files` and `git diff-tree` in the checkout that the agent had just worked in, under that checkout's `.git/config`, `.git/info/attributes`, `.git/hooks` and index, all of which the agent can write. The text of this item before this round said that `core.fsmonitor` needs code from `npm test`; it does not, the validator started it. A partial clone that the agent sets up (`extensions.partialClone` and a promisor remote with an `uploadpack` program) would start a program for any object that is missing. The validator now starts no `git` process in the checkout's repository: every one runs in the scratch repository, which has no configuration, attributes, hooks or remote of the checkout's (`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL`, `GIT_ATTR_NOSYSTEM`, `HOME` and `XDG_CONFIG_HOME` point into the scratch directory), takes the objects through an alternates file and copies of the refs, `HEAD` and shallow file, and reads the index file and the working tree as data (the working tree against an index of its own that starts as the base commit's tree). The configuration of the scratch repository now sets `core.alternateRefsCommand` to a command that lists nothing (the scratch repository holds copies of the refs, which `--all` reads), and a test reads the trace of a run that reads a bundle and fails against the validator of the previous round. A checkout whose refs are in the reftable format, or whose object format is neither `sha1` nor `sha256`, is refused, because the scratch repository cannot read it. AC22 lists the tests; those about a program, the index or the working tree fail against the validator of the previous round. One place that a pull request could be made of was still read for its paths and not for its value: the index. The QA stage of round 1 of the fresh run that completed the second loop (2026-11-07) staged a bump of `gh_aw_schema_version` and put the working tree's registry back, which left HEAD and the working tree at the base's value, and the validator exited `0`: it asked the index for paths under `.github/workflows/` only. It now reads the registry from the index file as well (`git cat-file blob :docs/_meta/registry.yaml` in the scratch repository, which reads that file as data, as `git diff-index --cached` does), and an index without the entry, or with an object that cannot be read, holds an absent value, as a commit without the registry does. *Still open:* the validator reads objects as the content-addressed data that they should be and does not hash them again; the read-only mount is derived from the lock file and none of this was observed in a live Actions run, so a mount that is writable, or a `GITHUB_ENV` file that the engine step can reach, would let the agent rewrite the staged copy or `SDLC_BASE_SHA`; whether the agent step can write the home directory of the runner was not observed either (the scratch repository cuts off the global configuration and attributes for that reason); a patch is read against the base commit that the run started from, whereas `safe_outputs` applies it to the target branch as it stands when that job runs, and the result of that merge is not read; and the post-steps run on the host with the rights of the runner, where the second `verifyCommands` entry of each lab project runs `npm ci` and `npm test` from the checkout that the agent edited, after the validator has finished: code that the agent wrote can change the patch and bundle files and the staged copy then, and any `git` that those commands, or the steps after them, run in that checkout reads its configuration, so that a program that the agent configured there runs at that point and not inside the validator. The validator cannot stop what runs after it; the remedy is to run those commands where the agent cannot write, which changes the design of the job and not this item.
