#### [SLIDE 4] · Six Permissions, Zero Autonomous Merges

> *⏱ 3 min · running 0:07 → 0:10*

> 👁 **SHOW** Three cards, left to right: a key, a dashed box, a padlock.

The security design has three layers, in the order the agent meets them. Each one is meant to hold if the one before it fails.

First, identity. The orchestrator acts as a single GitHub App, and its permission list is short and fixed: write access to contents, pull requests, issues, actions and variables, plus read access to metadata. That list is one data file that ships with the engine package, app-permissions.json. The bootstrap code compares whatever the App actually holds against that file. If the App has an extra permission or a higher level than listed, such as the right to change workflows or administer repositories, the command aborts and tells you nothing was written.

Second, the sandbox. The agent runs inside the GitHub Agentic Workflows Firewall, a container behind a network allowlist. For the drift audit that allowlist is two domains, docs.github.com and github.blog. For the mechanical cascade it's empty. The job also runs in gh-aw strict mode, and dependencies are installed before the agent starts, with install scripts switched off, so the agent never needs the network to run tests.

Third, the gates. After the agent finishes, deterministic steps run outside the agent's prompt. For drift, those are the project's own test commands, in order, and the first non-zero exit fails the job. For the AI cascade, an immutable-gates script also checks that locked files show zero diff. Only if all of that passes does the safe-outputs job run. It's the only place a pull request is opened, and auto-merge is off.

That's the title: six permissions, and a person is the last step every time.

#### [SLIDE 7] · S3 · Hybrid Push + ETag Event Router

> *⏱ 3 min · running 0:15 → 0:18*

> 👁 **SHOW** Four numbered rows. The last one has a dashed border and a circular arrow. That is the safety net.

I'll trace one merge through S3. Rows one to three are the fast path, and row four is the safety net.

Row one is the push. This repository carries a small workflow called the merge bridge. When a pull request merges to its main branch, it mints a short-lived token for the App and sends a repository dispatch to its own router. The event is named upstream underscore pr underscore merged, and its payload has six fields, including the merged commit, the pull request number and a correlation id. The other upstreams don't get the bridge, because it would need the App's private key, and that key can reach every installation of the App. We don't copy it anywhere.

Row two is the check. The router wakes up and reads that edge's state variable. Then it asks GitHub for the upstream's latest commit, sending the stored ETag in an If-None-Match header. If nothing changed, GitHub answers 304, and a 304 doesn't count against the primary rate limit. If something changed, the router compares the new head with the recorded state and runs the edge's cheap preflight checks, so a commit that changes nothing material, like a refreshed timestamp, doesn't start a cascade.

Row three is the dispatch. Otherwise the router starts the cascade workflow for that edge and passes the correlation id along, so the dispatch, the run and any failure issue share one id you can search for.

Row four is the safety net, and for every other upstream it's the main path. Four times a day, at 17 minutes past the hour, the same router runs on a schedule. Not on the hour, because that's when GitHub delays scheduled runs the most, and sometimes drops them. If a developer pushes straight to main, or an upstream has no bridge, or a dispatch gets dropped, the poll still sees the new head. That's the hybrid: the push is fast where we have it, and the poll catches everything else.

The router has two safeguards. Runs are serialized per edge, in a concurrency group that never cancels a run in progress, so two runs can't corrupt the state. And if a revision fails twice, the router stops and waits for a person instead of retrying forever.

The answer is B. I'll start with why the other two fail.

A has the pull request opening with a warning. That would make the gate advisory, and the design doesn't allow advisory gates. A failing post-step fails the agent job, and safe outputs depends on that job, so no pull request exists at all.

C has the router resetting the state variable. The router isn't in this path. A failed gate is recorded as one failure against that revision, and after two failures the router stops and waits for a person.

B is right because the check that decides isn't the agent's. The prompt can ask the agent to be careful, but it can't change which files the gate treats as locked. That list is data in sdlc.yaml, under the edge's immutable gates, and the script that enforces it runs after the agent has finished.

Locked covers three things. First, paths that must show zero diff. Second, the companion test files of the sibling workflows, which also must not move. Third, named blocks inside the edge's own tests, which must stay byte for byte what they were before the agent started. Change any of those and the script fails the job.

#### [SLIDE 12] · Declarative, Sandboxed, Self-Cascading

> *⏱ 1 min · running 0:29 → 0:30*

Three rules, one per card.

Declare the fleet as data. Watch addresses, verification commands and dependency edges all live in one manifest, so a reviewer can read the intent in a diff.

Never let an agent grade its own homework, and never hand it the write token. Bound the turn, sandbox the network, and run the checks where the agent can't edit them.

And match the cascade mode to the job. If a script can do the import, let the script do it, and spend the agent only where judgment is needed.

Each card names the specification that owns that rule; in the standalone deck those references open the files on GitHub for collaborators. The plan file holds the whole plan, with every claim traced to a source.
