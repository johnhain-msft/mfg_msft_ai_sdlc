#### [SLIDE 4] · Six Permissions, Zero Autonomous Merges

> *⏱ 3 min · running 0:07 → 0:10*

> 👁 **SHOW** Three cards, left to right: a key, a dashed box, a padlock.

The security design has three layers, in the order the agent meets them. Each one is meant to hold if the one before it fails.

First, identity. The orchestrator acts as a single GitHub App, and its permission list is short and fixed: write access to contents, pull requests, issues, actions and variables, plus read access to metadata. That list is one data file that ships with the engine package, app-permissions.json. The bootstrap code compares whatever the App actually holds against that file. If the App has an extra permission or a higher level than listed, such as the right to change workflows or administer repositories, the command aborts and tells you nothing was written. Both the instance and the engine are public, so that file is there for anyone to read. The engine's repository also runs a leak guard over every tracked file and its whole history, looking for identifiers that must not be published.

Second, the sandbox. The agent runs inside the GitHub Agentic Workflows Firewall, a container behind a network allowlist. For the drift audit that allowlist is two domains, docs.github.com and github.blog, plus the Microsoft Learn server the agent queries. For the mechanical cascade it's empty. The job also runs in gh-aw strict mode. In the administration drift job, dependencies are installed before the agent starts, with install scripts switched off, so the agent doesn't need the network to run tests.

Third, the gates. After the agent finishes, deterministic steps run outside the agent's prompt. For drift, those are the project's own test commands, in order, and the first non-zero exit fails the job. For the AI cascade, an immutable-gates script also checks that locked files show zero diff. Only if all of that passes does the safe-outputs job run. It's the only place a pull request is opened, and auto-merge is off.

That's six permissions, and a person is the last step every time.

#### [SLIDE 7] · S3 · Hybrid Push + ETag Event Router

> *⏱ 3 min · running 0:15 → 0:18*

> 👁 **SHOW** Four numbered rows. The last one has a dashed border and a circular arrow. That is the safety net.

I'll trace one merge through S3. Rows one to three are the fast path, and row four is the safety net.

Row one is the push. This repository carries a small workflow called the merge bridge. When a pull request merges to its main branch, it mints a short-lived token for the App and sends a repository dispatch to its own router. The event is named upstream underscore pr underscore merged, and its payload has six fields, including the merged commit, the pull request number and a correlation id. The other upstreams don't get the bridge, because it would need the App's private key, and that key can reach every installation of the App.

Row two is the check. The router wakes up and reads that edge's state variable. Then it asks GitHub for the upstream's latest commit, sending the stored ETag in an If-None-Match header. If nothing changed, GitHub answers 304, and a 304 doesn't count against the primary rate limit. If something changed, the router compares the new head with the recorded state and, for the edges that declare them, runs cheap preflight checks, so a commit that changes nothing material, like a refreshed timestamp, doesn't start a cascade.

Row three is the dispatch. Otherwise the router starts the cascade workflow for that edge and passes the correlation id along, so the dispatch, the run and any failure issue share one id you can search for.

Row four is the safety net, and for every other upstream it's the main path. Four times a day, at 17 minutes past the hour, the same router runs on a schedule. Not on the hour, because the start of the hour is a high-load time, when GitHub can delay scheduled runs and sometimes drop them. If a developer pushes straight to main, or an upstream has no bridge, or a dispatch gets dropped, the poll still sees the new head. That's the hybrid: the push is fast where we have it, and the poll catches everything else.

The router has two safeguards. Runs are serialized per edge, in a concurrency group that never cancels a run in progress, so two runs can't corrupt the state. And if a revision fails twice, the router stops retrying it instead of looping forever.

#### [SLIDE 12] · Declarative, Sandboxed, Self-Cascading

> *⏱ 1 min · running 0:29 → 0:30*

> 👁 **SHOW** Three cards. Each one names the specification that owns its rule.

Three rules, one per card.

Declare the fleet as data. Watch addresses, change policy, verification commands and dependency edges all live in one manifest. A versioned engine turns it into workflows, so a reviewer reads the intent in a diff, and the code that acts on it is pinned by tag.

Never let an agent grade its own homework, and never hand it the write token. Bound the turn, sandbox the network, and run the checks outside the agent's turn.

And match the cascade mode to the job. If a script can do the import, let the script do it, and spend the agent only where judgment is needed.
